# 情侣点菜 App · 架构与开发方案

> **版本 v2.0（定稿）** · 2026-10-18 · 仅 Android · ≤5 人内部使用 · 不上线
> 配套：`docs/需求基线.md`（需求真相源）· `docs/schema.sql`（已执行验证）· `docs/接口契约.md` · `docs/部署手册.md`

---

## 0. 一句话

一对情侣共用一个私有空间，双方都能加菜、点菜、接单做饭，数据实时互见；服务器在国外偶尔连不上时，App 照样能用，连上后自动补齐。

**所有设计围绕三件事**：强隔离、离线可用、两个人同时改不丢数据。

## 1. 场景约束（先钉死，否则一切选型都是空谈）

| 维度 | 事实 | 直接的架构后果 |
|---|---|---|
| 用户规模 | ≤ 5 人，2~3 对情侣，内部测试 | **不要**微服务 / Redis / K8s / 分库分表 |
| 部署 | 单台 2C2G 云服务器（吉隆坡） | 连接池小、必须开 swap、本地磁盘存图 |
| 网络 | 跨国，**会抖动甚至短时不通** | 离线优先；请求必须设超时；增量补漏是刚需 |
| 域名 | `food.fmcoral.com` + HTTPS | Caddy 自动证书，省掉 Nginx+certbot |
| 图片 | 服务器本地磁盘，无 OSS | 上传接口 + 随机文件名 + 备份含图片 |
| 上架 | 不发商店 | 不办软著/ICP，不接厂商推送通道 |

### 量化指标

| 指标 | 目标 | 说明 |
|---|---|---|
| 并发 | 峰值 < 10 请求/秒 | 5 个人，真不需要担心 |
| API 延迟 | p99 < 500ms（跨国含 RTT） | 吉隆坡 → 国内约 80~150ms，加上处理时间 |
| 同步延迟 | 在线 < 1s，离线后重连 < 5s 补齐 | WS 推 + cursor 补 |
| 可用性 | 99% 即可 | 挂了不影响生活，不做多活 |
| 单空间数据量 | < 2000 条菜品 / 5000 条订单 | 一年内不可能超 |

> **结论先行**：这套系统用单体 + 单库就能轻松支撑，任何"为了将来扩展"的复杂度都是纯负债。

## 2. 技术选型（含被否决的选项）

| 层 | 选择 | 被否决 | 理由 |
|---|---|---|---|
| 客户端 | **Flutter**（仅 Android） | 原生 Kotlin、RN | UI 动画一致；`drift` 提供成熟本地 SQLite；只出 apk，不背 iOS 负担 |
| 后端 | **Fastify 5 + TypeScript** | NestJS、Go、Java | I/O 密集足够；WS 生态最顺；与小团队开发节奏匹配 |
| 数据库 | **PostgreSQL 16**，手写 SQL | MySQL、MongoDB、ORM | 关系模型天然契合；约束能落到数据库层；本项目查询简单，ORM 只会挡路 |
| 实时 | **WebSocket**（@fastify/websocket） | 纯轮询、SSE | 双向 + 低延迟；SSE 无法双向，轮询费电 |
| 反向代理 | **Caddy** | Nginx + certbot | 自动 HTTPS，配置文件 5 行 |
| 图片 | 本地磁盘 + 客户端压缩 | OSS / COS | 你说不用 OSS；5 人一年约 750MB，磁盘完全够 |
| 部署 | **Docker Compose** | K8s、裸机 systemd | 一条命令起，重启自愈；2G 机器上 Docker 开销可接受 |
| 密码 | **scrypt**（Node 内置） | bcrypt、argon2 | 零依赖；接口留好，要换 argon2id 只改一个函数 |

## 4. 核心设计一：强隔离

### 4.1 两道防线

```
① JWT 里带 coupleId  → 绝大多数请求零额外查询
② 所有 SQL 强制 WHERE couple_id = $1  → 漏写就查不到数据
③ assertOwned() 二次校验 → 针对单实体操作（PATCH/DELETE）
```

**越权统一返回 404，不返回 403。**
理由：403 等于承认"这个 id 存在"，404 什么都不泄露。实现成本为零——查不到就是查不到。

### 4.2 分类归属：每对情侣各自一套

绑定成功时，为这对情侣复制预设：

```
种类（6）：荤菜 · 素菜 · 汤 · 主食 · 甜品 · 其他
口味（7）：重口 · 清淡 · 辣 · 甜 · 酸 · 香 · 无
```

不全局共用，因为用户自定义分类必然带私人色彩（"她做的菜""待开发"），全局共用会让 5 个人的列表迅速变脏。

### 4.3 双维度分类为什么用两张表

| | 一张表 + `kind` 字段 | **两张表（采用）** |
|---|---|---|
| 种类唯一性 | 只能应用层保证 | ✅ `dish_type_links.dish_id` 做主键，数据库强制 |
| 语义 | 靠约定 | ✅ 表名即语义 |
| 未来加"菜系"维度 | `kind` 越塞越多 | ✅ 加一张表 + 一张关联表 |

**已验证**：给同一道菜插第二个种类 → `duplicate key violates dish_type_links_pkey`。

## 5. 核心设计二：离线同步（技术心脏）

### 5.1 本地是副本，不是缓存

| | 缓存 | **副本（采用）** |
|---|---|---|
| 离线能读 | ✅ | ✅ |
| 离线能写 | ❌ | ✅ |
| 代价 | 无 | 必须解决冲突 |

既然离线能写，就必然出现"同一道菜被两地各改一次"。**这就是版本号存在的唯一原因。**

### 5.2 三层机制

```
① 乐观锁（version）—— 检测冲突
   PATCH 必带 version
   UPDATE ... WHERE id=? AND version=?  → 影响 0 行 = 409

② 字段级合并 —— 解决冲突
   客户端收到 409 → 拉最新 → 逐字段比较
   只有「同一字段双方都改且值不同」才让用户选
   本地记录 dirty 字段，只提交改过的字段（否则会覆盖对方改的其他字段）

③ 事件日志（sync_events）—— 补齐断线期间的变化
   写操作在同一事务内追加事件，id 单调递增
   客户端存 cursor，重连后 GET /sync/events?since=cursor
```

### 5.3 时间戳的铁律

**所有 `created_at` / `updated_at` 由服务端 `now()` 生成。**
客户端时间只用于本地展示排序，**绝不参与任何冲突裁决**——否则改一下手机时间就能让记录"永远最新"。

### 5.4 离线新建必须客户端生成 UUID

```dart
// ❌ 错：等服务器返回 id
final res = await api.post('/dishes', {...});   // 离线时这一步永远等不到
final id = res.data.id;

// ✅ 对：本地先有 id
final id = const Uuid().v4();
await localDb.insert(id: id, ..., dirty: true);
queue.append(SyncOp.create(id, payload));
```

服务端 `POST /dishes` 接受客户端传入的 `id`，已存在则幂等返回。**不改这里，离线新建必然重复建菜。**

### 5.5 明确不做：CRDT / OT

菜谱是**结构化字段（名称/照片/分类/备注）**，不是一段散文。字段级 LWW + 冲突提示完全够用。上 CRDT 会让复杂度翻 3 倍，而体验上一个像素都不会变。

## 6. 核心设计三：关系生命周期

### 6.1 状态机

```
                     ┌─────── dissolved（归档，数据保留）
                     │            ▲
pending ──► active ──┤            │ B 同意 / 超管强制
                     │            │
                     └──► dissolving
                            │  ▲
                  B 拒绝 / A 撤回│
                            └──┘ 回到 active
```

### 6.2 解散规则（按你的定稿）

| 规则 | 实现 |
|---|---|
| 不能单方解散 | 发起后进入 `dissolving`，必须 B 同意才生效 |
| B 可拒绝 | `rejected` → 回到 `active`，申请记录留档 |
| **无冷静期、无超时自动执行** | 不做定时任务 |
| A 可撤回 | B 回应前，A 随时可撤回 |
| 冻结期只读 | 所有写接口检查 `status='dissolving'` → 409 |
| B 长期不响应 | **A 联系超管，超管手动强制解散**（`forced_by_admin`） |
| 解散后 | 数据归档保留；双方回「未绑定」，可重新绑定他人 |
| 客户端 | 收到 `couple.dissolved` → 全屏提示 → **立刻清空本地库** → 回登录页 |

**为什么冻结期要给 A 保留撤回按钮**：如果不给，A 撤回不了、B 不拒绝，两人就卡死在只读状态。"撤回"和"拒绝"只要有一条走通就能解冻。

### 6.3 绑定流程的坑（实测踩到过）

```
A 生成邀请码（A 的 token: coupleId = null）
  → B 加入，couples 变 active
    → A 手里的 token 仍是 coupleId = null
      → A 建菜 → 403「还没有绑定关系」
```

**修法（必须做）**：绑定成功接口**同时返回 B 的新 token**，并向 A 推 `couple.bound` 事件，A 端收到后静默 refresh。

## 7. 点菜：状态机由后端裁决

```
pending ──► accepted ──► cooking ──► served ──► completed
   ├──► rejected（对方拒绝，可带理由）
   └──► cancelled（下单人可撤）
```

| 规则 | 说明 |
|---|---|
| 权限 | 下单人只能 `cancelled`；接单/做饭/上菜只能由**对方**操作 |
| 非法跃迁 | `pending → served` 直接拒绝（409） |
| 快照 | `order_items` 冻结 `dish_name` / `dish_image_key` |
| 上限 | 单笔 ≤ 50 道；不算总价，`price` 仅展示 |
| 已下架的菜 | 禁止下单（409），但历史订单不受影响 |

> 客户端的状态机只是 UI 提示。用户改手机时间、抓包重放都能绕过，**后端拒绝非法跃迁是唯一可靠的保障**。

## 8. API 契约（摘要）

完整定义见 `docs/接口契约.md`。约定：

- 前缀 `/api`，资源用复数，JSON
- 错误体走 RFC 9457：`{ type, title, status, detail, errors?, request_id }`
- 除注册/登录/刷新外全部需 `Authorization: Bearer <token>`
- 列表接口一律分页（`limit` 默认 20，最大 100）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/auth/register` `/auth/login` `/auth/refresh` `/auth/logout` | 认证 |
| POST | `/couples/invite` `/couples/join` | 绑定 |
| GET | `/couples/me` | 伴侣信息 |
| POST | `/couples/dissolve/request` `/:id/approve` `/:id/reject` `/:id/withdraw` | 解散流程 |
| GET/POST | `/dish-types` `/dish-flavors` | 分类（每对情侣一套） |
| GET/POST/PATCH/DELETE | `/dishes` | 菜品（PATCH 必带 version） |
| POST | `/uploads` | 图片上传（≤5MB，白名单扩展名） |
| GET | `/dishes/changes?since=` | 增量拉取 |
| POST | `/orders` · `/orders/:id/transition` | 点菜 |
| GET | `/sync/events?since=` | 事件流补漏 |
| WS | `/ws` | 实时通道（先 auth 后订阅） |
| GET | `/admin/couples` `/admin/couples/:id/menu` `/admin/couples/:id/orders` | 超管只读 |
| POST | `/admin/couples/:id/dissolve` · `/admin/users/:id/reset-password` | 超管动作 |
| GET | `/admin/status` | 系统状态 |

## 9. 超管体系

### 9.1 定位

**独立身份，不参与情侣绑定。** 同一登录页登录，凭手机号+密码直达管理页，无独立入口。

### 9.2 权限矩阵

| 能力 | 允许 | 落审计 |
|---|---|---|
| 情侣列表（活跃/解散中/已归档三 Tab） | ✅ | — |
| 查看菜品（名称/图/分类/备注） | ✅ 只读 | ✅ |
| 查看订单（内容/状态流水） | ✅ 只读 | ✅ |
| 用户手机号（脱敏中间 4 位） | ✅ | ✅ |
| 重置用户密码 | ✅ | ✅ |
| 解散任一对情侣 | ✅ | ✅ |
| 系统状态（在线数 / 最后活跃 / 今日操作 / 磁盘 / 备份） | ✅ | — |
| **修改/删除任何业务数据** | ❌ 403 | ✅ 记拒绝 |
| 生成测试数据 | ❌ 不实现 | — |
| 查看密码 hash | ❌ | — |

### 9.3 安全约束

- 超管手机号 `18756459919` 写入 `.env` 预置
- 密码只从 `ADMIN_PASSWORD` 读取，**代码中绝不硬编码**
- 超管登录额外限流：5 次/10 分钟
- 所有超管动作写 `admin_audit_log`（含 IP）

## 10. Android 客户端

### 10.1 页面（8 页，定稿）

| # | 页面 | 核心职责 |
|---|---|---|
| ① | 登录 | 自动登录；离线可进；超管无感进管理页 |
| ② | 注册 | 手机号 / 密码 / 昵称 |
| ③ | 配对 | 双模式同页（生成码 / 输码） |
| ④ | 今日 | **状态驱动**，首屏只显示"现在该干什么" |
| ⑤ | 菜单 | 浏览/点菜双模式；种类+口味可叠加筛选 |
| ⑥ | 订单 | 按状态分组 + 时间轴 |
| ⑦ | 我们 | 个人信息、伴侣、同步状态、退出 |
| ⑧ | 菜品编辑 | 四项字段 + 冲突合并提示 |

### 10.2 安卓专有坑（必须处理）

| 坑 | 现象 | 解法 |
|---|---|---|
| 后台被杀 | 切回要等几秒 | 回前台**立刻** `pullGap()`，不等 WS |
| 弱网半连接 | WS 看似连着但收不到消息 | 30s ping，2 次无 pong 就重连 |
| 跨国抖动 | 请求挂死 | 连接超时 5s / 读超时 15s，指数退避重试（只重试 5xx 和网络错误） |
| 明文 HTTP | Android 9+ 默认拦截 | 走 HTTPS，不需要 `usesCleartextTraffic` |

### 10.3 换 IP 不影响已装 App

连接地址走**域名** `food.fmcoral.com`，不硬编码 IP。换服务器时只改 DNS A 记录，客户端零改动。同时在设置页保留"手动填服务器地址"作为兜底。

## 11. 安全与隐私

| 风险 | 防护 |
|---|---|
| 越权看别人的菜 | `couple_id` 强过滤 + 越权 404 |
| 手机号枚举 | 登录失败统一文案 |
| 暴力破解 | 登录 8 次/分钟；邀请码错 5 次锁 1 小时；超管 5 次/10 分钟 |
| Token 泄露 | access 15min + refresh 轮换（用一次作废） |
| 密码泄露 | scrypt 加盐；日志脱敏 |
| 图片被遍历 | 随机 UUID 文件名 + 扩展名白名单，不暴露目录结构 |
| 日志泄露隐私 | 结构化日志自动脱敏 `authorization` / `password` / `refreshToken` |
| 超管滥用 | 全部动作落审计日志；只读 + 脱敏 |
| 分手后数据 | 归档保留（超管可查），双方本地立即清空 |

## 12. 部署与运维

### 12.1 拓扑

```
Caddy :443 (自动证书) ──► Fastify :3000 ──► PostgreSQL :5432
                                              /data/images
                                              /data/backup
```

### 12.2 必做项

| 项 | 说明 |
|---|---|
| **swap 2G** | 2G 内存跑 Node + PG + Caddy，不开口子会被 OOM Killer 杀 |
| **restart: unless-stopped** | 断电重启后自己起来 |
| **每日备份** | `/data/backup/*.tar.gz`（库 + 图片全量），保留 3 份，03:00 执行 |
| **健康检查** | `/health`（存活）· `/ready`（DB 连通） |
| **不暴露 5432** | 数据库只在内网，安全组只开 22 / 80 / 443 |

### 12.3 备份的边界（要清楚）

同盘备份只能防「误删」「逻辑损坏」，**不能防「磁盘物理损坏」**。你说不做异地备份，那就接受这个边界。

## 14. 已知边界（明确接受，不是遗漏）

1. **不做异地备份** → 磁盘物理损坏时数据无法恢复
2. **不做锁屏推送** → App 不在前台时收不到通知，打开才看到
3. **不做超管自动兜底** → B 长期不响应需人工找超管
4. **不做图片 CDN** → 跨国访问图片比文字慢，首屏会有轻微加载感
5. **不做多语言** → 仅中文
6. **不做 iOS** → 你要的
