## 0. 一句话定义

一个**仅安卓**的情侣点菜 App：一对情侣共用一个私有空间，双方都能加菜、点菜、接单做饭，数据实时互见，服务器在国外偶尔连不上时仍可正常使用。

---

## 1. 使用场景（决定一切的前提）

| 项 | 事实 | 对架构的影响 |
|---|---|---|
| 用户规模 | **内部测试，≤ 5 人，不上线** | 不要微服务、不要 Redis、不要 K8s、不要分库分表 |
| 关系数量 | 支持多对（2~3 对），**强隔离** | 每张业务表带 `couple_id`，查询必须过滤 |
| 部署 | **单台 2C2G 云服务器（吉隆坡）** | 保守内存配置、必须开 swap |
| 网络 | 跨国线路，**会抖动/短时不通** | 离线优先 + 超时 + 重试 + 增量补漏 |
| 域名 | `food.fmcoral.com`，**需要 HTTPS** | Caddy 自动签发（不用 Nginx+certbot） |
| 图片存储 | **服务器本地磁盘**，不用 OSS | 上传接口 + 随机文件名 + 备份含图片 |
| 上架 | **不上应用市场，不上线** | 不办软著、不办 ICP、不做渠道推送 |

### ✅ 要做

| 模块 | 内容 |

| 超管 | 只读查看情侣/菜品/订单；解散；重置密码；系统状态 |

| 不做 | 原因 |

| 短信验证码 | 5 个用户，省掉通道成本和复杂度 |
| 应用商店上架、软著、ICP | 不上线，直接发 apk |

| 聊天/私信 | 不缺，微信已解决 |
| 金额结算、AA、账单 | 点菜是清单不是账单，`price` 仅作展示 |
| 超管生成测试数据 | 你明确不需要 |
| 异地备份 | 只要本地 3 天快照 |

## 3. 关键决策记录（按对话顺序，含变更）

### D-01 客户端：Flutter（仅构建 Android）

- **决定**：Flutter，只出 apk，不做 iOS。
- **备选**：原生 Kotlin（性能最优但开发慢）、RN（安卓适配坑多）。
- **理由**：UI 动画一致性好（点菜体验靠动画），`drift` 提供成熟的本地 SQLite 离线能力。
- **代价**：包体约 20MB，需学 Dart。

### D-02 后端：Node.js (Fastify) + TypeScript + PostgreSQL

- **决定**：Fastify 5 + TypeScript，PostgreSQL 16，手写 SQL（不用 ORM）。
- **备选**：NestJS（样板过多）、Go（与前端类型不通）、Java（重）。
- **理由**：I/O 密集场景性能足够；WebSocket 生态最顺；与 Flutter 侧可共享 TS 类型定义。
- **代价**：CPU 密集场景弱（本项目无此需求）。

### D-03 同步策略：事件日志 + 乐观锁 + WebSocket

- **决定**：写操作在**同一事务**内追加 `sync_events`（自增 id 即游标）；实体带 `version` 乐观锁；WS 实时推送；断线用 `GET /sync/events?since=cursor` 补齐。
- **备选**：纯轮询（费电、延迟高）、纯 WS 广播（无冲突解决）。
- **理由**：正确性有保障；弱网/切后台/换手机都能精确补漏。
- **代价**：多一张事件表，客户端要维护 cursor 与 dirty 字段。
- **明确不做**：CRDT / OT。菜品是结构化字段，不是自由文本，字段级 LWW 已足够；上 CRDT 会让复杂度翻 3 倍而无体验收益。

### D-04 离线优先：本地 SQLite 是「副本」，不是缓存

- **决定**：本地可读**可写**；离线可新建菜品；客户端生成 UUID（不依赖服务端返回 id）。
- **理由**：跨国线路抖动是常态，不能把「连不上」当异常处理。
- **代价**：必须做冲突合并（D-05）。
- **约束**：所有时间戳以**服务端 `now()`** 为准，客户端时间只用于本地展示，不参与冲突裁决。

### D-05 冲突处理：version 检测 + 字段级合并

- **决定**：`PATCH` 必带 `version`，不匹配返回 409；客户端拉最新后**按字段 diff**，只有同一字段双方都改才让用户选；本地记录 dirty 字段，只提交改过的字段。
- **理由**：只做版本号会导致「冲突时二选一，丢掉一边的改动」。

### D-06 数据隔离：行级多租户，每张表带 `couple_id`

- **决定**：所有业务表含 `couple_id`；所有查询强制过滤；越权统一返回 **404**（不是 403，避免泄露「该 id 存在」）。
- **理由**：隔离逻辑只有 `currentCouple(req)` 一处入口，便于审计；`couple_id` 可直接作未来分片键。

### D-07 绑定：邀请码 6 位，必须走正常流程

- **决定**：`POST /couples/invite` 生成 6 位码（24h 有效）→ 对方 `POST /couples/join`。
- **明确否决**：「初始化时写死一对关系」（我之前提过，已撤回）。
- **否决理由**：换手机/重装后拿到新 `user_id`，写死的关系无法自愈，必须 SSH 上服务器手改数据库。为省一天工作量，换来每次换机都要人工介入。
- **附加防护**：邀请码输错 5 次锁定该设备 1 小时；创建者可主动作废重发。
- **必须做对**：绑定成功瞬间，**双方都要换发 access token**（旧 token 里 `coupleId` 是 null，会导致 403）。这是实测踩到的坑。

### D-08 关系生命周期：绑定后**不可由单方解散**，但可申请

```
pending → active → dissolving → dissolved（归档）
                      ↓  B 拒绝 / A 撤回
                    active
```

- **决定**：A 发起解散 → 进入 `dissolving` → **B 可选择「同意」或「拒绝」**；A 在 B 回应前可**撤回**。**不设冷静期，不做超时自动执行。**
- **`dissolving` 期间双方只读冻结**：能看、不能改；顶部一条二合一状态条（状态 + 操作按钮）。
- **B 长期不响应**：由 A 联系超管，超管手动强制解散（不做 3 天自动）。
- **解散生效**：`status='dissolved'` + `archived_at`；数据**归档保留不删**；双方回到「未绑定」，可重新绑定他人。
- **客户端**：收到 `couple.dissolved` → 全屏提示 → **立刻清空本地 SQLite** → 回登录页。
- **变更说明**：会话中期我建议过「24h 冷静期自动解散」，你否决并要求「B 可拒绝、无冷静期、卡住找超管」。以你的决定为准。

### D-09 分类：两个独立维度

| 维度 | 基数 | 预设 | 自定义 |
|---|---|---|---|
| **种类** | 单选（1 道菜 1 个） | 荤菜 / 素菜 / 汤 / 主食 / 甜品 / 其他 | ✅ |
| **口味** | 多选（可 0..n） | 重口 / 清淡 / 辣 / 甜 / 酸 / 香 / 无 | ✅ |

- **决定**：两张独立表 `dish_types`、`dish_flavors`，**不是**一张表加 `kind` 字段。种类唯一性用 `UNIQUE(dish_id)` 在关联表上强制。
- **归属**：**每对情侣各自一套**，创建关系时复制预设（不全局共用）。
- **筛选**：种类（单选）与口味（多选）**可叠加取交集**。
- **保留自由标签 `tags`**：口味是受控词表，标签是自由词（如「10 分钟」「妈妈的菜」）。UI 上统一渲染为胶囊，用户无需感知二者差异。

### D-10 点菜：互相点，状态机由后端裁决

```
pending → accepted → cooking → served → completed
   ├→ rejected（对方拒绝，可带理由）
   └→ cancelled（下单人可撤）
```

- **权限**：下单人只能 `cancelled`；接单/拒单/做饭/上菜只能由**对方**操作（不能给自己接单）。
- **快照**：`order_items` 冻结 `dish_name` / `dish_image_url`，菜品改名或删除不影响历史订单。
- **上限**：单笔最多 **50 道**；不算总价，`price` 仅展示。

### D-11 超管：独立账号，只读 + 管理动作

- **决定**：`users.is_admin = true`；**超管不参与情侣绑定**（禁止调绑定接口）；同一登录页登录，凭手机号+密码**无感直达管理页**，无独立「管理员登录」入口。
- **权限边界**：

| 能力 | 允许 |
|---|---|
| 查看情侣列表（昵称、绑定时间、状态） | ✅ |
| 查看**菜品**（名称/照片/分类/备注） | ✅ 只读 |
| 查看**订单**（内容与状态流水） | ✅ 只读 |
| 查看用户手机号（中间 4 位脱敏） | ✅ |
| 重置某用户密码 | ✅ |
| 解散任一对情侣 | ✅ |
| 查看系统状态（在线数、最后活跃、今日操作数、磁盘、备份） | ✅ |
| **修改/删除任何业务数据** | ❌ 一律 403 |
| 生成测试数据 | ❌ 不做 |
| 查看密码 hash | ❌ |

- **预置账号**：手机号 `18756459919`，密码从 `.env` 的 `ADMIN_PASSWORD` 读取，**代码中绝不硬编码**。
- **UI**：管理页三个 Tab —「活跃 / 解散中 / 已归档」；右上角「退出登录」。

### D-12 传输与配置

- **HTTPS**：Caddy 自动证书，指向 `food.fmcoral.com`。
- **换 IP 不影响已安装的 App**：客户端连接地址走**域名**而非硬编码 IP；同时保留 App 内可改服务器地址的设置项作为兜底。
- **明文 HTTP**：因走 HTTPS，**不需要** `usesCleartextTraffic`。⚠️ 若证书出问题临时降级 HTTP，需另行处理（见部署手册）。

### D-13 图片存储

- **决定**：存服务器本地磁盘（`/data/images`），**不用 OSS**。
- **上传**：`multipart`，单张 ≤ 5MB；服务端存随机 UUID 文件名 + 扩展名白名单；返回受控访问路径。
- **压缩**：**客户端**压缩（最长边 1600px，JPEG 质量 80%），服务端不二次压缩（省 CPU）。
- **备份**：必须与数据库一起打包（否则恢复后全部菜品无图）。

### D-14 备份与运维

- **路径**：`/data/backup/couple-menu-YYYYMMDD-HHmm.tar.gz`
- **内容**：**全量**（`pg_dump` + `/data/images`）
- **频率**：每日 03:00
- **保留**：**3 份**（`find -mtime +3 -delete`）
- **明确不做**：异地备份、异地恢复演练
- **必须做**：swap（2G 内存）、`restart: unless-stopped`、`/health` 探活

## 4. 页面基线（8 页，不再增加）

| # | 页面 | 层级 | 核心职责 |
|---|---|---|---|
| ① | 登录 | 未登录 | 自动登录；离线可进；超管无感进管理页 |
| ② | 注册 | 未登录 | 手机号/密码/昵称，三个字段 |
| ③ | 配对 | 未绑定 | 双模式同页：生成邀请码 / 输入邀请码 |
| ④ | 今日 | Tab 1 | **状态驱动**，首屏只显示「现在该干什么」 |
| ⑤ | 菜单 | Tab 2 | 双模式：浏览 / 点菜；筛选可叠加 |
| ⑥ | 订单 | Tab 3 | 按状态分组 + 时间轴（生活记录） |
| ⑦ | 我们 | Tab 4 | 个人信息、伴侣、同步状态、退出登录 |
| ⑧ | 菜品编辑 | 三级 | 四项字段 + 冲突合并提示 |

**贯穿原则**

1. 写操作先改本地、立刻有反馈，网络在后台异步
2. 同步失败**不弹窗**，只在卡片角落标云朵图标，3 秒自动重试
3. 只有 ⑦ 我们 页暴露技术状态（同步状态、待同步条数）
4. 「已解散」用全屏提示，不用 toast
5. 空状态给引导动作，不写「暂无数据」
